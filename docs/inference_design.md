# Inference design

## Purpose

The inference layer generates physically plausible species and reaction candidates when local registry data are missing.

The purpose is not to replace curated data.

The purpose is to help users and developers discover likely missing reactions and missing species for low-pressure plasma modeling.

## Relationship To Enrichment, Imports, Snapshots, And Promotion

Inference is not the same as enrichment:

- **Inference** creates rule/template-generated candidates when registry data
  are missing. Inferred items are marked `status: inferred` and are review
  targets, not evidence-backed data.
- **Enrichment** fills prepared registry gaps from configured local/offline
  providers such as local registry data, internal files, NIST snapshots,
  Argonne/ATcT-style thermochemistry snapshots, optional `chemicals`, or ion
  reaction tables.
- **Imported local DB data** comes from user-provided local files or internal
  snapshots. It should normally be marked `status: imported` unless it has been
  reviewed and assigned `literature_supported` or `curated`.
- **External data snapshots** are created outside the core runtime by
  `external_data_tools/` or by manual preparation. They must be reviewed before
  being used as source-profile inputs.
- **Promotion** is the explicit review step that copies selected prepared or
  candidate data into curated `registry/`. It is dry-run by default and requires
  `reactgen promote --apply` for mutation.

`reactgen generate` remains local-registry-only. It does not fetch external
data, run enrichers, import cross sections, or promote candidates.

## Default behavior

Inference must be disabled by default.

Existing registry-only generation should produce the same result unless inference is explicitly enabled.

Recommended default:

```yaml
inference:
  enabled: false
```

## Basic configuration

Recommended case input extension:

```yaml
inference:
  enabled: false
  include_inferred_species: true
  include_inferred_reactions: false
  min_confidence: 0.4
  max_products: 3
  max_fragment_depth: 1
```

## Candidate status

Every inferred species and inferred reaction must clearly show that it is inferred.

Example:

```yaml
status: inferred
confidence:
  score: 0.6
  basis:
    - charge_and_element_balanced
    - generated_by_template
    - energy_unknown
inference:
  rule: dissociative_charge_transfer
  parent_species:
    - CF4
  notes:
    - Candidate generated by rule, not curated data.
```

Do not silently promote inferred data to curated registry data.

## Hard filters

Hard filters reject candidates.

Current required hard filters:

- species references must be resolvable or generated as candidates
- total charge must be conserved
- elemental composition must be conserved
- product count must not exceed `max_products`
- duplicate reaction IDs must be avoided

If a candidate fails a hard filter, it should not be emitted.

## Soft filters

Soft filters keep candidates but reduce confidence or mark missing data.

Recommended soft filters:

- unknown reaction energy
- unknown threshold
- unknown cross-section data
- unknown DNT required property
- unusual composition
- too many radical products
- no literature source
- template-only support

Soft filters should be visible through `confidence.basis` and `missing_*` fields.

## Confidence

Confidence should be simple and explainable.

Recommended format:

```yaml
confidence:
  score: 0.55
  basis:
    - charge_and_element_balanced
    - plausible_fragment
    - generated_by_known_template
    - energy_unknown
```

Do not present confidence as a precise physical probability.

It is a prioritization score for review.

## Species candidate generation

The first implementation should be conservative.

Recommended minimal scope:

- parse simple chemical formulas
- compute mass from composition when atomic masses are known
- generate parent cations
- generate parent anions
- generate simple one-fragment-loss neutral radicals
- generate simple fragment ions

Example:

```text
CF4 -> CF4+
CF4 -> CF4-
CF4 -> CF3 + F
CF4 -> CF3+
```

Avoid generating a large number of chemically speculative species.

## Formula parser scope

Initial supported examples:

```text
Ar
CF4
O2
N2
H2
SiH4
C2F6
Cl2
C2H6
CHF3
```

The first version does not need to support:

- parentheses
- hydrates
- isotopes
- charges embedded in formula strings
- structural isomers
- excited-state notation

Unsupported formulas should fail gracefully.

## Reaction template status

Current implementation is intentionally minimal.

Implemented templates:

- electron parent ionization: `e + M -> 2e + M+`
- ion-neutral parent charge transfer: `A+ + M -> A + M+`

The inference layer should not generate cross-section tables.

If cross-section data are missing, the candidate should say so.

Planned/design templates, not complete current behavior:

- electron attachment: `e + M -> M-`
- electron dissociation: `e + AB -> e + A + B`
- dissociative ionization: `e + AB -> 2e + A+ + B`
- dissociative attachment: `e + AB -> A- + B`
- excitation: `e + M -> e + M*`, only when excited states are registered
- resonant charge transfer: `A+ + A -> A + A+`
- dissociative charge transfer: `A+ + AB -> A + fragment+ + fragment`
- atom or group transfer: `A+ + BC -> AC+ + B`
- collisional dissociation: `A+ + BC -> A+ + B + C`
- association or clustering: `A+ + M -> AM+`, optional and low priority unless supporting data are available

## DNT relevance

Not every inferred ion-neutral reaction is immediately ready for DNT+/DNT+DM calculation.

Each ion-neutral channel should carry:

```yaml
dnt_class: long_range_charge_exchange
data:
  dnt:
    status: missing_energy
    missing_for_complete_dnt:
      - deltaE_products_minus_reactants_eV
```

DNT readiness should be evaluated by the DNT input exporter.

## Recommended module structure

```text
src/plasma_reactgen/inference/
  __init__.py
  provider.py
  species_candidates.py
  reaction_templates.py
  screening.py
  scoring.py
  candidate_writer.py
```

## Provider design

Use a small provider structure.

Recommended interface:

```python
class ChannelProvider:
    def get_channels(self, pair, context):
        ...
```

Recommended implementations:

```text
RegisteredReactionProvider
InferredReactionProvider
CompositeReactionProvider
```

Behavior:

```text
CompositeReactionProvider
  -> get registered channels
  -> if inference is disabled, return registered channels only
  -> if inference is enabled and include_inferred_reactions is true, append inferred channels
  -> registered channels take priority over duplicate inferred channels
```

Current integration uses this provider shape for normal generation only when
inference is explicitly enabled. The implemented inference templates are
conservative parent ionization and parent charge transfer candidates. Required
product species may be created in memory for validation and propagation, but
they are not written into curated registry files.

Normal generation and `infer-candidates` use the provider and
candidate-writer path.

## Candidate output workflow

Inferred candidates should first be written to a separate candidate directory.
This workflow is developer tooling; it is not the default `generate` path.

Current output:

```text
candidate_registry/
  species/
  reactions/
  summary.yaml
```

`summary.yaml` includes `registry_mutated: false` to make the review-only
contract explicit.

Developer command:

```text
reactgen infer-candidates CASE --registry registry --output candidate_registry
```

Recommended developer workflow:

```text
1. Run candidate inference.
2. Inspect candidate_registry/.
3. Edit or reject questionable candidates.
4. Promote selected candidates with reactgen promote --apply.
5. Run dev checks.
6. Run normal generation.
```

## Integration with network generation

Normal generation should remain registry-only by default.

Inferred reactions should be included in generated networks only when explicitly enabled:

```yaml
inference:
  enabled: true
  include_inferred_reactions: true
```

Even when included, inferred reactions must remain marked as inferred in output files.

In-memory inferred species used by these channels also remain marked as inferred.
They are generation artifacts, not promoted registry entries.

## Testing guidance

Add small tests only.

Recommended tests:

- inference config parses correctly
- inference disabled preserves existing generation behavior
- simple formula parsing works
- generated candidate reactions pass charge balance
- generated candidate reactions pass element balance
- candidate output goes to `candidate_registry/`

Avoid large golden-file tests.
